# Git을 초심자에게 와닿게 설명하려면

CloneUp 제품·온보딩·설정 「용어 안내」·문서 작성의 **설명 원칙**입니다.

**고정 규칙**

- 화면 버튼·탭 이름(**만들고 올리기**, **받기**, **동기화**, **충돌 취소**, **커밋 내역** 등)은 **교체하지 않는다**.  
- 목표는 “지금 이해되는 비유”만이 아니라 **6개월 뒤에도 모순을 일으키지 않는 모델**이다.  
- 정확성과 친절함이 충돌하면 **정확성**을 택하고, 대신 **문장을 짧게** 한다.

---

## 0. “금지 목록만”의 함정

제약을 “깨지기 쉬운 비유 금지”로만 촘촘히 하면 결과는 둘 중 하나다.

1. **비유를 통째로 포기** → 무미건조한 설명서 → “와닿게”와 충돌  
2. **검증 불가능한 제약** → “깨지는 비유인지 스스로 알면 애초에 안 썼다” → 프롬프트에 있어도 없는 것과 같음  

그래서 설계 원리를 **셋**으로 바꾼다.

| # | 원리 | 의미 |
|---|------|------|
| 1 | **금지 목록이 아니라 통과 시험** | 비유를 미리 막지 말고, 반드시 통과할 **구체 상황**에 대입. 실패하면 폐기 |
| 2 | **유효 범위 선언 의무** | 비유는 어딘가에서 깨진다. 깨지는 지점을 **문서에 미리 적으면** 사고가 아니라 설계 |
| 3 | **비유는 명사(자리·관계), 동사는 사실** | “어디/무엇”만 비유. “실제로 무슨 일이 일어나는지”는 정확한 서술. 비유가 동작까지 대신하면 거짓말 |

관측된 실패 비유 **6개**는 아래에 고정한다.  
**금지 목록은 더 늘리지 않는다.** 새 실패 사례는 금지 목록이 아니라 **시험 항목**에 추가한다.

## 1. 비유 부하 시험 (출력 전)

비유 후보를 정한 뒤 아래 상황에 대입한다.  
짧은 답·짧은 카드는 **A만** 돌려도 된다 (A 4개가 실패의 대부분을 걸러냄).

### A. 필수 (하나라도 실패 → 즉시 폐기)

1. 수정한 파일 5개 중 **2개만** 골라 커밋할 수 있는가?  
2. **인터넷 없이** 커밋 10개를 쌓고 나중에 한 번에 push가 설명되는가?  
3. **브랜치 2개**가 동시에 **같은 커밋**을 가리킬 수 있는가?  
4. **reset과 revert** 차이가 이 비유 안에서 구분되는가?  

### B. 확장 (실패 시 유효 범위를 **축소 선언**)

5. “커밋은 했지만 push는 안 한 상태”를 부를 이름이 있는가?  
6. merge가 갈래를 “합쳐 없애는” 게 아니라 **새 커밋을 하나 만드는 것**임이 설명되는가?  
7. conflict가 왜 “Git이 못 정하는 상황”인지  
8. untracked 파일이 있다는 것  
9. .gitignore로 일부러 추적하지 않음  
10. clone이 단순 파일 복사가 아니라 **역사**를 가져옴  
11. 남이 먼저 push해 내 push가 거절됨  
12. 과거를 지우기보다 **새 기록을 덧붙이는** 방식

## 2. 고정 금지 비유 (예외 없음 · 변형·완곡 포함)

시험 A를 통과하지 못하는 것으로 **관측된** 것만 둔다.

| 금지 | 이유 (한 줄) |
|------|----------------|
| 백업 / 복사본 보관 | push = 폴더 통째 업로드 오해; 커밋 안 한 파일 설명 불가 |
| 구글 드라이브·드롭박스·자동 클라우드 | Git은 **명시적** 단계 |
| 게임 세이브포인트 / 저장·불러오기 (선형) | 브랜치에서 붕괴; staging 못 담음 |
| 타임머신 / 과거로 돌아가기 | reset·revert·checkout 구분 파괴 |
| 브랜치 = 폴더 복사본 | merge에서 붕괴 |
| USB 옮기기 / 단순 파일 전송 | staging·로컬 커밋 단계 삭제 |

## 3. 통과하는 주 비유: 원고 제출 (문서당 최대 2개 중 하나)

| 자리 | 비유 (명사·관계) | 정식 | 클론업 화면 말 |
|------|------------------|------|----------------|
| 1 | 책상 위 원고 | working tree | 작업 폴더 / 로컬 폴더 |
| 2 | 봉투에 넣을 장 | staging / `git add` | (UI에 세분 없을 수 있음 — 개념은 설명) |
| 3 | 봉인·라벨·**내 서고** | local repo / `git commit` | **커밋** |
| 4 | **출판사** | remote / `git push` | **GitHub**, **올리고 보내기** |

**동사는 사실로** (예):

- 비유: “봉투에 넣을 자리를 고른다”  
- 사실: `git add`는 해당 파일의 **현재 내용을 staging area에 기록**한다.

**유효 범위 선언 (필수 예시 문장):**

> 이 비유(원고 제출)는 **네 자리와 보내기/남기기 관계**까지다.  
> 브랜치 이름표·merge 그래프·reflog는 비유 없이 설명한다.

**대응표를 한 번만** 제시하고, 같은 문서에서 같은 단어만 쓴다.  
비유 옆 **정식 영어 용어 병기**. 우리말만으로 대체해 검색 불능으로 만들지 않는다.

### 브랜치 (둘째 비유 후보 — 필요 시만)

- 비유: 커밋 사슬 위의 **이름표(스티커)**; HEAD = 지금 보고 있는 곳  
- 금지: 폴더 통째 복사  
- 유효 범위: “이름표가 어디를 가리키는지”까지. 복잡한 히스토리 재작성은 비유 밖.

## 4. 서술 금지 (친절이 해가 되는 것)

- 의인화: “Git이 알아서 / 기억해 준다”  
- 빈 안심: “걱정 마세요”, “어렵지 않아요”, “그냥 외우세요”  
- 사고 종료: “일단 이렇게만 하면 됩니다” (뒤에서 이유를 쓴다고 **명시**하면 허용)  
- 정확도 희생 단순화 → 줄일 수 없으면 **범위 밖**으로 빼라  

명령 이름 오해 고지 (한 번):

| 이름 | 오해 | 사실 쪽 |
|------|------|---------|
| `add` | 추가 | **선별** → staging |
| `origin` | 원본 | 흔한 **기본 별명** |
| `checkout` | 한 가지 일 | 맥락에 따라 **다른 일** |

## 5. 문서·기능 목차 원칙

1. **앞부분:** add → commit → push (또는 클론업: 만들고 올리기 / 동기화) **성공 경로**  
2. **직후:** “왜 여러 단계였나” → **네 자리** (입장료로 개념 요구 금지)  
3. 이상적 장문 문서: 단계마다 `git status` **영어 상태 문자열** 전/후  
   (`Untracked files` / `Changes not staged for commit` / `Changes to be committed`)  
4. 에러 섹션 제목 = **에러 원문** (검색 유입). 최소 후보:  
   authentication failed / non-fast-forward / src refspec main does not match any /  
   vim 탈출 / main·master 불일치  

클론업 UI: 상태 문구·확인창·로그·「다음:」로 **자리 착각**을 줄이는 쪽  
= **보여주면서 해주는 도구** (대신만 해주면 README·용어 안내와 서로 무효화).
